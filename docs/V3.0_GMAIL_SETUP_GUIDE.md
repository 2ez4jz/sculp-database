## JZ 在 Google Cloud 的操作

1. 在工作室控制的 Google Cloud Project 启用 **Gmail API**。
2. Google Auth Platform 配置 Branding、Audience、Data Access。Workspace 组织内部应用按实际组织选择 Internal；普通 Gmail 使用 External，测试阶段把工作室主邮箱加入测试用户。
3. 仅请求 `https://www.googleapis.com/auth/gmail.readonly`。不添加 send、modify、compose 或 mail.google.com 全权限。
4. 创建 OAuth Client，类型 **Web application**。Authorized Redirect URI 必须完整匹配当前 Supabase 环境：
   `https://YOUR_PROJECT_REF.supabase.co/functions/v1/sculpy-gmail?action=callback`
   测试和正式项目分别登记，不能使用前端 GitHub Pages 地址作为此回调。
5. 保存 Client ID 与 Client Secret 到 **Supabase Edge Function Secrets**。只读 Client ID 也不需要写进前端。
6. `gmail.readonly` 是 restricted scope。外部正式使用的验证及可能的安全评估需按 Google Console 实际要求完成；不能承诺个人测试配置等于生产审批。外部 Testing 项目中这类 refresh token 可能 7 天失效，需要重新授权。参考下方 Google 官方文档。
7. 应用公开使用前，在 OAuth 配置中提供准确的隐私说明，涵盖业务范围过滤、服务端存储、AI 可选处理、保留/断开清理及不自动发信。不将邮件用于训练通用模型。

## Supabase 服务端配置

| Secret / 环境变量 | 内容 |
| --- | --- |
| `GMAIL_CLIENT_ID` | Google Web OAuth Client ID |
| `GMAIL_CLIENT_SECRET` | Google OAuth Client Secret |
| `GMAIL_TOKEN_KEY` | 独立随机 32 字节、base64url 无 padding（43 字符），用于 AES-GCM |
| `GMAIL_REDIRECT_URI` | 上面登记的完整回调 URL |
| `GMAIL_APP_URL` | 授权成功返回的 SCULP OS HTTPS 地址，正式 Pages 为 `https://2ez4jz.github.io/sculp-database/`；测试环境填测试前端 |
| `GMAIL_EXPECTED_EMAIL` | 唯一获准连接的工作室主邮箱，其他邮箱会被拒绝 |
| `GMAIL_ALLOWED_ORIGINS` | 精确前端 origin，以逗号分隔；Pages origin 为 `https://2ez4jz.github.io` |
| `GMAIL_WORKER_KEY` | 独立随机至少 32 字符，供调度器调用；不能放入前端 |
| `GMAIL_BUSINESS_LABEL_ID` | 可选 Gmail 业务标签的 ID；不填则仅导入已知业务地址 |
| `GMAIL_ALIASES` | 可选、明确属于工作室的发件别名，用逗号分隔 |
| `GMAIL_AUTOMATIC_AI` | 默认关闭；设 `true` 后每轮最多尝试一条摘要，仍须在账户设置显式开启邮件 AI |
| `GMAIL_AI_MODEL` | 可选；沿用现有项目模型配置；本次不新建 OpenAI 密钥 |

沿用平台注入的 Supabase 服务端配置及已存在的 `OPENAI_API_KEY`。不要把 service role、Google token、加密密钥或 worker key 放入 `src/config.js`。加密密钥轮换前必须设计密文重加密或重新授权；不要直接改 key 后期望旧 token 仍可解密。

本次未新增这些真实 secret；公开回调配置探针返回 setup_required，说明必需配置缺失或无效。请在服务的 Secrets 管理页面安全填写。OAuth Client Secret 不需要发给助手。

## 部署及授权顺序

当前正式环境已安装本次两条迁移和 Gmail v1；不要重复执行迁移。下述部署步骤供新建独立测试环境参考，当前继续从安全配置核对和真实授权验收开始。

1. 审核本次候选迁移，并在独立环境执行 `20261112192341_gmail_communication.sql`。
2. 部署 `sculpy-gmail` Edge Function。`verify_jwt=false` 是为了 OAuth GET 回调；每个浏览器 POST 都另外验证 Auth.getUser 和数据库 active 业务角色，worker 验证单独 key，回调验证一次性 state/PKCE。
3. 发布匹配的测试前端。在 **系统设置 → Gmail Integration** 点击连接，选择工作室主邮箱并审核只读权限。成功后回到 SCULP OS，确认连接状态。
4. 先不启用调度，点击“导入业务历史邮件”，用测试客户完成分批导入；重试核对同一 Gmail Message ID 不重复。
5. 给 Edge `GMAIL_WORKER_KEY` 和 Supabase Vault 的 `sculpy_gmail_worker_key` 配置同一值。按批准环境修改并执行 `docs/GMAIL_SCHEDULER.sql`。调度每 5 分钟运行，但大邮箱首次导入可能需要多轮，不承诺所有邮件 5 分钟内处理完。
6. AI 需要管理员在 Gmail 设置中显式开启。模型调用沿用现有服务端配置、`store:false`，不提供发信工具。先使用测试邮件实测信息分级与草稿，禁止只凭模拟测试宣传真实质量。
7. 最后才申请生产授权、迁移与发布。仓库提交或 CI 通过不等于生产发布。

## 数据范围与断开策略

- 默认只处理 CRM 联系邮箱与非测试询盘邮箱；业务标签是明确扩展范围的选择。不要将私人标签指定为业务标签。
- 增量同步可以读取消息头来判断关联，但不保存无关邮件正文、联系人或 AI 输入。
- 相同地址按 lower/trim 匹配，不删除 Gmail 的点或 plus 标签，不按姓名合并。重复邮箱的已有客户视为歧义，不自动合并或自动关联；先人工核对联系邮箱，或在业务标签范围内明确关联。
- 首次导入的历史邮件不批量生成旧提醒。新邮件只生成内部任务，不新增手机推送权限。报价提醒还需要明确的 CRM 报价状态及实际已发邮件证据。
- 断开首先在数据库停用连接并使 worker lease 失效；销毁本地密文 token，清空正文、主题、发收件人、附件名称、AI 摘要和草稿；保留 Gmail ID、时间、方向和业务关联审计。随后尝试 Google revoke；失败时提示到 Google 账户权限页手动撤销。Gmail 原件不删除。
- 已发出的外部请求不能追回；断开后的在途同步/AI 结果会被数据库拒绝保存。托管备份可能仍包含历史记录，保留期需要在正式环境单独核实。
