# SCULP OS 3.0：数据库结构与迁移方案

日期：2026-11-12。状态：本地候选，未应用生产。

## 复用模型

| 关系 | 现有实现 | 本阶段选择 |
| --- | --- | --- |
| 客户 → 多笔订单 | `bookings.client_id → clients.id` | 保留；不改 UUID 或编号 |
| 询盘 → 订单 → 客户 | `website_enquiries.booking_id`、`bookings.originating_enquiry_id` | 复用既有事务；不以姓名自动归并 |
| 订单 → 多条沟通 | `communication_records.booking_id`；询盘沟通保留 enquiry_id | 保留原始来源与摘要确认流程 |
| 订单 → 日程 | `starts_at/ends_at/timezone` | 先显示近期服务日期；外部日历另做授权设计 |
| 客户/订单 → 任务 | `reminders.client_id/booking_id/assigned_to` | 复用，允许独立任务；同时关联时核对客户一致性 |
| 订单 → 发票 → 多笔收退款 | `invoices.booking_id → payments.invoice_id`、`payments.refund_of` | 复用合同金额及退款方向，不改银行资金 |
| 来源追踪 | 客户 `referral_source`、询盘 attribution/UTM、订单来源 | 保留，不用空字符串伪造来源 |
| 权限 | `profiles.role/active` 及既有检查函数 | 仅 active owner/operations 可访问新增业务 RPC |

当前不需要新增客户、订单、日程或付款表。未部署的旧 `crm_tasks` 不作为本次依赖；后续须明确合并方案，避免两套任务系统并存。

## 候选迁移

文件：`supabase/migrations/20261112184732_sculp_os_phase1_foundation.sql`，由 Supabase CLI `migration new` 创建。

- 新增 4 个 public SECURITY INVOKER 包装 RPC 和 4 个 private 实现：`sculpy_os_overview`、`sculpy_os_clients`、`sculpy_os_create_task`、`sculpy_os_create_client`。
- private 实现因现有表不向浏览器开放读取，需要 SECURITY DEFINER；使用空 search_path、全限定表名、`auth.uid()` 和现有 active 业务角色检查。PUBLIC/anon 执行权显式撤销，仅 authenticated 可调用，仍受函数内部授权限制。
- 不新增表、列、种子数据或宽泛表授权；撤销 reminders 的 TRUNCATE/REFERENCES/TRIGGER 浏览器权限。
- 查询为只读、按多伦多日历计算；列表有明确上限，统计在数据库全量核算。
- 应收复用 `sculpy_private.contract_value`，只统计有效 confirmed/completed 主合同，按已收减退款核算；CAD 之外及缺价单独提示。不把报价、预算或定金字段当作净收入。
- 任务创建由当前管理员明确确认，记录到 reminders 与 audit_events；关联双方均须有效且一致。任务 UUID 在未确认回执期间保持不变，重复同请求不重复建任务。任务不是自动推送规则。
- 客户最小新增仅姓名/来源，写 created_by 和审计；同请求重放匹配原始内容，同名候选提示核对，不自动合并。当前不能通过此入口建立同名不同人的完整客户资料。
- 不依赖硬编码 JZ/Miranda UUID，不采用可编辑 user_metadata 作为授权依据。

## 测试环境与兼容性

使用 `scripts/support/cloud-database.mjs` 建立全新本地 PGlite，每次销毁隔离测试数据库，不接触生产。新增测试核对完整迁移链、权限、重试、关联、财务口径及旧订单保留。该环境不是托管 Supabase：PostgREST schema cache、实际 Auth、并发连接和 Storage 仍须在独立 Supabase 测试项目验收。

生产历史与仓库迁移目录存在漂移。发布前应从当前生产 schema 建立受控测试副本，仅应用本次新增迁移，确认依赖函数/枚举签名和 grants。不要执行未评估的旧 crm_tasks 迁移，也不要用 `db reset` 或强制迁移历史修复处理生产。

## 发布前条件与顺序

1. JZ 审核候选代码和本报告；明确生产发布授权。
2. 核实可用备份时间、保留期、Storage 文件备份及恢复人员；在独立环境实际恢复并记录结果。数据库备份不自动包括 Storage 对象字节。
3. 在已授权测试环境按生产状态演练候选迁移；跑真实 PostgreSQL 权限/并发及 API/账号测试。
4. 确认旧客户、订单、询盘数量及关联不变；用 JZ/Miranda 测试账号验证 Dashboard、客户、任务及禁用账户。
5. 先迁移接口，再发布前端；检查资源版本、RPC 暴露及页面回读。不要为了修权限放开表级 grants。
6. 聊天后端产品知识更新须与线上 v52 内容合并，再单独审核发布；本 PR 不授权重发旧 Edge Function。

## 非破坏性回退

- 前端恢复基线提交，保留新增任务、客户、审计及已有业务数据。
- 必要时先 revoke authenticated 对新增 public/private 创建 RPC 的 EXECUTE，停止新写入。只读查询可保留供恢复。
- 不 DROP 业务表，不删除新任务/客户，不用旧备份直接覆盖已有新业务。
- 本地具备事务回滚和数据保留测试；生产级备份/恢复演练未完成，不能据此宣称可发布。
